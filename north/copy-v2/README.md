## הדבקה בחנות

1. ב־[products.js](../js/products.js) מחליפים רק את `desc` של המוצר בעל אותו `id`. הרשומות בחבילה הן עדכוני תיאור בלבד, ולא תחליף לאובייקט המוצר המלא. משאירים את שאר השדות, ובפרט `contents`, `variants`, `kosher` ו־`kosherNote`. JSON תקין גם כערך JavaScript.
2. את תוכן [faq.json](faq.json) מעתיקים כערך של המערך `FAQ`. השדות הם `q` ו־`a`, לפי מבנה הקוד הקיים. לחלופין מעתיקים את מקטע ה־HTML.
3. את [business.html](business.html) מעתיקים לעמוד או לאזור המתאים. המקטע מכיל תוכן וקישור לטופס העסקים הקיים. הוא אינו מחליף את הטופס, את הטיפול בשליחה או את שדותיו.
4. במיילים מעתיקים את `subject` לשדה הנושא ואת `body` כטקסט עם פסקאות, או את מקטע ה־HTML כגוף. כל קובצי ה־HTML הם מקטעים להדבקה, ללא מעטפת מסמך. הקישורים מלאים ומתאימים לכתובת החנות ב־GitHub Pages; אם עוברים דומיין, מעדכנים את `storePath` ב־render.mjs ומייצרים מחדש.
5. התוצאה הצפויה: 12 תיאורי מוצר, דף עסקים, 15 שאלות ותשובות ושלוש תבניות מייל, ללא שינוי בתכולה ובתמחור. מריצים את הבדיקות למטה לאחר ההדבקה או שינוי מקור.

החבילה אינה מחוברת לחנות במסגרת PR זה. לא נערך קוד קיים ולא מתבצעת שליחת מייל.

## תנאי שימוש במיילים

המשתנה היחיד הוא `{{orderNumber}}`, מספר ההזמנה. אין משתנה של שם לקוח, כתובת או מספר טלפון. מזינים את המספר ממערכת ההזמנות, מקודדים אותו כטקסט בטוח ל־HTML בגוף וכטקסט בשורת הנושא, ובודקים שאין תווי בקרה או שורה חדשה בנושא. לא משאירים משתנים פתוחים במייל שנשלח.

| תבנית | מתי משתמשים |
|---|---|
| `order-confirmation` | אחרי קבלת התשלום ואישור זמינות, או אחרי אישור טלפוני לתשלום באיסוף ואישור זמינות. חזרה מעמוד הסליקה אינה מספיקה |
| `shipping` | להזמנה מאושרת שנבחר לה משלוח באזור, או משלוח מיוחד שאושר ותואם. זהו מייל פרטי מסירה; הוא אינו מודיע שהמארז יצא או מבטיח מועד שלא נבדק |
| `cancellation` | אחרי שביטול ההזמנה אושר ונרשם. לא שולחים אותו כאישור לקבלת בקשת ביטול. הזכאות להחזר וסכומו נקבעים לפי נסיבות העסקה והתקנון |

אלו תבניות לערכי הזמנה שייבדקו בעת השימוש. התקנון אינו מוכיח שאירוע בהזמנה מסוימת כבר התרחש. ההבחנה מתועדת גם בטבלת הטענות.

## בדיקה ויצירה מחדש

משורש הריפו, ללא התקנת חבילות:

```sh
node --test north/copy-v2/copy.test.mjs
```

בסביבה שבה בידוד תהליך הבדיקה של Node אינו זמין, ב־Node 22 ומעלה:

```sh
node --test --test-isolation=none north/copy-v2/copy.test.mjs
```

ליצירה מחדש של HTML וטבלת הטענות לאחר עדכון ה־JSON:

```sh
node north/copy-v2/render.mjs
node north/copy-v2/render.mjs --check
```

הבודק סורק את כל קובצי ה־JSON וה־HTML של התוכן בתיקייה, כולל קבצים חדשים שיתווספו. `claims.json`, `sources.json` ו־`review.json` הם קובצי ראיות וביקורת, ואינם תוכן להדבקה. גם הדוח, ההוראות וקוד הבדיקות אינם נכללים בסריקת הטקסט למסירה: הם כוללים מילים אסורות וציטוטים לצורך התיעוד והבדיקות השליליות.

נבדקים סימני קריאה, לרבות צורות Unicode וקידוד HTML; מילות מבצע והנחה, לרבות הטיות, תחיליות ומספר ביטויים מקבילים; ומספרי טלפון ישראליים ובינלאומיים בפורמטים נפוצים. נבדקים גם שני משפטים למוצר, מזהים, כשרות, התאמת HTML ל־JSON, שלמות המיפוי למקורות וארבעת סבבי הביקורת. זו בדיקת מילים ופורמטים, ואינה יכולה לזהות כל ניסוח אפשרי של הבטחה או הטבה: את המשמעות בדקתי ידנית.

חתימות המקור מכוונות לקומיט שנבדק. אם מקור השתנה, גם בשדה שאינו טקסט, הבדיקה תיכשל ותדרוש בדיקה חוזרת. שגרת הבדיקות הקיימת מריצה רק `tests/*.mjs`, ולכן יש להריץ את הבדיקה החדשה במפורש; לא נערך workflow במסגרת מגבלת הקבצים החדשים.
