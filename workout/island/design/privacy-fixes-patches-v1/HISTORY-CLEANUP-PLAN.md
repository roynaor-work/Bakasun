# הצעה לניקוי היסטוריית Git

**נדרשת החלטה נפרדת לפני כל שכתוב או שינוי refs.** החבילה הנוכחית מוסיפה תיקונים מוצעים לקבצים בגרסה הנוכחית. התוכנית שלהלן היא הצעה בלבד.

## החלטה נדרשת

בעל הריפו יקבע אם היקף החשיפה מצדיק שכתוב, אילו ענפים ותגים ייכללו, מה דרוש לשמירה משפטית ותפעולית, מי מוסמך לבצע את העבודה ומתי משביתים כתיבה למאגר. לפני ההחלטה יש להציג את תוצאות האומדן והבדיקה המקומית המפורטת להלן ואת השפעתן על ה־PR, הפריסה והגיבויים.

## שלבים מוצעים

1. **לצמצם חשיפה בגרסה הפעילה.** אחרי אישור החלת החבילה, לאמת את הקבצים הנוכחיים ואת תוצר Pages. לבטל או לסובב כל פריט גישה שאומת כסוד בערוץ תפעולי מורשה. להכניס התייחסות ליעד הפרטי בלבד לצד ממצאים על זהות, פרטי קשר או ראיות. שכתוב Git לא מבטל פריט גישה שנחשף.
2. **למפות את היקף החשיפה.** לתעד במלאי מוגן את כל ה־refs שניתן לקרוא, כולל ענפי עבודה, תגים ו־PR refs, את שמות העבר של נתיבי הראיות ואת העותקים ב־Pages, ב־Actions, בקבצי Release וב־LFS אם קיים. להתחיל בנתיבי `patches/0001-private-data.json` ובמיקומים של PA‑001 בביקורת. לסרוק גם הודעות קומיט, שדות author/committer, תגיות, ארכיונים ותמונות. בדוח פומבי לשמור נתיבים, ספירות ומזהי ממצאים בלבד.
3. **להכין גיבוי מבודד וחומרי סינון פרטיים.** ליצור mirror ועותק התאוששות מוצפן עם בקרת גישה ובדיקת שחזור. לשמור אותם מחוץ למאגר הציבורי. להכין רשימות נפרדות לנתיבים שלמים שאפשר להסיר, לערכים שצריך להשחיר בקבצים שנשארים בשימוש, להודעות קומיט ותגים ולמיפוי כתובות המחברים. הרשימות נשמרות במיקום פרטי ומאושר, ללא שיתוף בלוגים. לשחזר נתיבי עבר ולהוסיף אותם לרשימות לפי תוצאות הסריקה.
4. **לבדוק שכתוב ב־mirror זמני ונפרד, אחרי אישור לניסוי.** לוודא שה־mirror טרי ומכיל את ה־refs שהוגדרו. התבנית הבאה מיועדת לעותק הניסוי בלבד. קובצי הקלט הם משתנים פרטיים, והאפשרויות נבחרות לפי המלאי שאושר.

   ```sh
   git filter-repo --sensitive-data-removal \
     --invert-paths --paths-from-file "$PRIVACY_PATHS_FILE" \
     --replace-text "$PRIVACY_BLOB_RULES_FILE" \
     --replace-message "$PRIVACY_MESSAGE_RULES_FILE" \
     --mailmap "$PRIVACY_MAILMAP_FILE"
   ```

   `--invert-paths` מתאים לראיות ולקבצים שלמים שנבחרו להסרה. בקבצים פעילים יש להשתמש בכללי השחרה או בטרנספורמציה שמקיימת את מבנה הקובץ. יש לבדוק את פורמט האפשרויות מול גרסת `git-filter-repo` המותקנת. ארכיונים, בינאריים, LFS ותמונות מצריכים בדיקה והחלטת נתיב נפרדות.
5. **למדוד תוצאות לפני שינוי מרוחק.** לבצע סריקה חוזרת מה־refs החדשים, להשוות רשימות ענפים ותגים, לבדוק את שינויי העצים ואת דוח שינוי ה־PR ולבדוק build, בדיקות ופריסה בסביבה מבודדת. לתעד את קומיטי ההשפעה הראשונים ואת סטטוס ה־refs בנתיבים ובספירות בלבד. לבדוק שהגיבוי המוגן נגיש לצוות השחזור.
6. **לקבל החלטת פרסום נפרדת.** רק באישור מפורש נוסף, לקבוע חלון הקפאת כתיבה ולהתאים את העדכון לרשימת refs מצומצמת ולמזהי ה־refs שנמדדו בעת ההקפאה. לטפל בהגנות ענף ובחתימת תגים מחדש. לא לפרסם אוטומטית mirror לכל ה־refs. לתאם מול GitHub טיפול ב־PR refs, תצוגות מקור ועותקים שבשליטת הפלטפורמה, ולהחליף תוצרי Pages ו־Actions שהוגדרו לטיפול.
7. **לאמת אחרי פרסום ולמנוע החזרה.** לבדוק מה המאגר והאתר מגישים בפועל, לרבות refs שהוחרגו ותוצרי פרסום שזוהו. לתאם clone חדש או rebase מבוקר של עבודה מקומית. להטמיע מניעת דחיפה חוזרת מההיסטוריה הישנה ולהגדיר משך שמירה ומועד פקיעה של הגיבוי המוגן.

## סיכונים ותוצאות צפויות

| תחום | השפעה ובדיקה |
| --- | --- |
| קומיטים, תגים וחתימות | לקומיטים מושפעים ולצאצאיהם יהיו מזהים חדשים. חתימות ותגים חתומים עשויים להידרש לחתימה מחדש. הפניות ל־SHA וגרסאות תלויות ידרשו עדכון. |
| סניפים, PR והגנות | השכתוב עלול לשנות או לנתק השוואות, תגובות ובדיקות CI. refs שלא נכתבו מחדש יכולים להמשיך להפנות לקומיטים הישנים. clone ישן עלול להחזיר את התוכן. |
| מידע משוכפל | forks, clones, ארכיונים והעתקות של צדדים שלישיים עשויים להישאר, וכך גם תוצרי פריסה ומטמונים עד לטיפול נפרד. הסרה מכל מקום אינה ניתנת להבטחה. |
| אובדן תפעולי | כלל רחב מדי עלול להסיר קובצי runtime או גרסאות נחוצות. תרגול השחזור והבדיקות בעותק מבודד נדרשים לפני ההחלטה. שחזור ה־refs הישנים עלול לפרסם מחדש את המידע. |
| קריטריון סיום | סריקה נקייה לממצאים המאומתים ב־refs שבשליטת הריפו ובתוצרי הפריסה שסוכמו, סוד שנחשף בוטל, סטטוס מתועד לכל משטח שנותר, וגרסאות האפליקציה המיועדות נבנות ועולות. |
